# SambaNAS2 changelog style (source of truth for automation)

This file supplements `.github/CHANGELOG_TEMPLATE.md`. The template describes a
generic `Added/Changed/Fixed` layout with dates; `sambanas2/CHANGELOG.md`
actually uses the emoji layout below with calendar RC versions and dated release
headings. Automation (and human edits) must follow this file.

## Headings

- Top is always `## Unreleased` (empty when nothing pending). The section must
  always exist, even when empty; a file without it is invalid.
- Versioned headings exist ONLY for released versions and are dated:
  `## [2026.11.0] - 2026-11-17`, `## [2026.11.0-beta.1] - 2026-11-20`.
- Until a version is released, ALL of its content lives under `## Unreleased`.
  Never add a versioned heading for an unreleased version.
- `config.yaml:version` (C) is source of truth for the upcoming release version;
  humans and the AI changelog action never bump it here.

## Release transitions (owned by CI, deterministic via `.github/scripts/changelog_release.py`)

- Release cut (stable or beta): promote `## Unreleased -> ## [<version>] - <date>`,
  leaving a fresh empty `## Unreleased` on top.
- Beta release: after the promote, strip the fresh empty `## Unreleased` (S2 = S1
  minus U) so the release/beta branch carries only the versioned section. The
  beta PR then targets the prerelease branch of the upcoming final version
  (e.g. `prerelease/sambanas2_<final-version>`).
- Release rolled back / not shipped: demote `## [<version>] ... -> ## Unreleased`
  so all content of that version returns to Unreleased.

## Version rules (content only, no transitions here)

- C == H (first versioned heading == C): append to `## Unreleased` only (Us1/Us4).
  Never bump versions here.
- C not in file + `Unreleased` non-empty: content is pending; promote at release time.
- C in older `##`: no duplication; only ensure `## Unreleased` exists.
- Never create `-beta`/`-dev` headings here; never add/remove `## Unreleased` in a
  way that leaves two heads. Transition commands are deterministic and CI-owned.

## Sections (only when non-empty)

- In the first versioned release (first `##` that is not `## Unreleased`),
  `### 🙏 Thanks` is always first and `### 🚨 Notes` always second,
  regardless of edit order. A deterministic normalization step re-sorts them.
- Remaining sections keep this order after Thanks/Notes:
  `### ✨ Features`, `### 🐛 Bug Fixes`, `### 🏗 Chore`,
  `### 💥 Breaking Changes`, `### 🔄 Migration Notes`.
- `### 🙏 Thanks`: keep short, release entries only (never in `## Unreleased`).
- `## Unreleased` itself needs no Thanks/Notes; use Features/Fixes/Chore only.

## SRAT entries (no dedicated section)

- There is NO `### 🐭 Features from SRAT` section. Historical `🐭` blocks in old
  releases stay untouched; new releases never add one.
- The used SRAT version is referenced once in `### 🏗 Chore`, with a link to the full
  upstream changelog, e.g.:
  `- Update SRAT to [v2026.9.0-rc15](https://github.com/dianlight/srat/blob/2026.9.0-rc15/CHANGELOG.md)`
- Only important user-facing SRAT changes are reported, inside the normal
  `### ✨ Features` / `### 🐛 Bug Fixes` sections, each suffixed with the source,
  e.g.: `- Interface IP resolution at config generation time (from SRAT v2026.9.0-rc15)`.
- Selection and wording is done by the AI changelog action: read
  `Dockerfile ARG SRAT_VERSION`, fetch that tag's `CHANGELOG.md` from
  `https://raw.githubusercontent.com/dianlight/srat/<ver>/CHANGELOG.md`,
  keep breaking/user-visible features and fixes, drop internal churn,
  Thanks/Roadmap noise and duplicates of add-on bullets.
